# Фильтр постановки инженерных задач и ТРИЗ — кандидат v1

Кратко: универсально требуются подтверждённые исходные данные, понятная цель и критерий результата. Техническое противоречие требуется только там, где задача действительно является инженерной задачей поиска/оптимизации и стандартный путь упирается в конфликт требований.

## Почему область действия ограничена

Не каждая задача проекта является ТРИЗ-задачей. Проверка хэша, редактура документа, поиск файла, публикация уже подготовленного материала или восстановление чата могут не содержать технического противоречия. Блокировать такие задачи из-за отсутствия искусственно придуманного «барьера» нельзя.

## 1. Универсальный входной минимум

Для любого профильного исполнения должны быть понятны:

1. **Подтверждённые исходные данные и контекст** — что известно фактически и какие источники доступны.
2. **Цель** — какое изменение или результат требуется получить.
3. **Критерий достаточности** — по какому проверяемому признаку можно остановить работу и считать текущую задачу выполненной.

Если критически важного элемента не хватает, задача переводится в подготовительный режим и запрашивается минимально необходимая информация.

Критерий не обязан быть числом. Для документа это может быть утверждённый набор требований; для диагностики — полученный измеряемый отчёт; для маршрута — фактическая доставка файла.

## 2. Симптом и причина

Сущность должна различать наблюдаемый симптом, известную причину и неизвестную причину.

Неизвестная причина **не блокирует диагностическую задачу**, если целью задачи как раз является её установление. В таком случае неизвестность фиксируется как предмет диагностики, а не выдумывается заранее.

## 3. Когда нужен ТРИЗ-фильтр

Дополнительный анализ противоречия применяется, когда одновременно выполняется хотя бы одно из условий:

- стандартное решение не достигает цели;
- улучшение одного свойства ухудшает другое существенное свойство;
- ограничения системы не позволяют применить очевидное решение;
- требуется найти новую конструкцию, способ или архитектуру, а не просто выполнить известную операцию.

Тогда фиксируются:

- **барьер** — что мешает достичь цели известным способом;
- **техническое противоречие** — какое полезное изменение вызывает нежелательное ухудшение;
- при необходимости **идеальный конечный результат (ИКР)** как ориентир поиска, но не как магическая формула, заменяющая проверку реальности.

## 4. Подготовительный режим

При нехватке данных:

    остановить профильное исполнение
    -> назвать конкретно, чего не хватает
    -> объяснить, почему это существенно
    -> предложить минимальный проверяемый способ получить данные

Не требуется писать «мотивированный отказ», если достаточно одного конкретного вопроса или диагностического шага.

## 5. Что запрещено

- придумывать техническое противоречие только ради прохождения шаблона;
- требовать известную причину до начала диагностики;
- объявлять задачу нерешаемой только потому, что она не является ТРИЗ-задачей;
- использовать ИКР вместо критериев безопасности и фактической проверки;
- подменять сбор исходных данных длинным теоретическим анализом.

## 6. Связь с общим каноном

Этот фильтр является профильным методом постановки инженерных задач и не отменяет общепроектный принцип:

    одна задача -> один проверяемый результат -> одна проверка

При конфликте с действующим универсальным файловым каноном или core-инструкцией выполнение останавливается до решения ОПЕРАТОРА/КООРДИНАТОРА.
