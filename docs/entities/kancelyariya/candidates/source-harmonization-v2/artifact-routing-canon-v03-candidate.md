# Канон короткой маршрутизации артефактов — кандидат v0.3

Кратко: для межсущностной передачи имя значимого артефакта должно сразу показывать отправителя и получателя, не превращаясь в технический роман.

## Статус

Эта редакция является кандидатом на замену `artifact-routing-canon-v02.md`. До утверждения ОПЕРАТОРОМ она не вводит новую обязательную норму.

## Главный принцип

Для значимого артефакта, который передаётся между Сущностями:

    <КОД_ОТПРАВИТЕЛЯ>__<смысловое-название>__<КОД_ПОЛУЧАТЕЛЯ>.<ext>

Пример:

    SHD__cryptoplatform-wave2-package__KOD.zip

Локальные рабочие файлы, которые не маршрутизируются между Сущностями, не обязаны иметь коды отправителя и получателя.

| Код | Сущность/роль |
|---|---|
| OPR | ОПЕРАТОР |
| KOO | КООРДИНАТОР |
| ARH | АРХИВАРИУС |
| SIS | СИСАДМИН |
| WEB | ВЕБМАСТЕР |

| VOL | ВОЛОНТЁР, код существует; профиль полномочий определяется отдельным источником |

## Неизвестный отправитель или получатель

Если отправитель неизвестен:

    UNK__old-package-for-review__ARH.zip

Артефакт может быть принят адресатом на ручную проверку, но происхождение должно быть помечено как неизвестное.

Если получатель неизвестен:

    SHD__unclear-cryptoplatform-note__UNK.md

Автоматическая доставка блокируется:

    blocked: target_unknown

## Риск-маркер

Риск не обязан находиться в имени. Если это помогает автоматической маршрутизации, допускается:

    SHD__tera-key-sanitized__R2__KOD.md

| Код | Смысл |
|---|---|
| R0 | обычный рабочий артефакт |
| R1 | требуется внимательная проверка |
| R2 | инфраструктура, публикация, ответственность или потенциально опасное действие |
| R3 | секреты, ключи, приватные данные; автоматическая пересылка запрещена |

R3 не отменяет общий запрет публиковать секреты. Если файл фактически содержит секрет, его нельзя «обезопасить» одним маркером в имени.

## Метаданные маршрута

Если имени недостаточно, допустим `artifact-card.json` либо существующий `manifest`. Не создавать оба только ради дублирования.

Минимальная карточка:

    {
      "from_entity": "SHD",
      "to_entity": "KOD",
      "artifact_kind": "source-intake",
      "risk_level": "R1",
      "topic": "cryptoplatform-wave2",
      "expected_action": "изучить пакет и вернуть замечания"
    }

## ПОЧТАЛЬОН

В этом документе ПОЧТАЛЬОН означает программный или операторский механизм маршрутизации артефактов. Само название не создаёт отдельную ИИ-Сущность и не наделяет её полномочиями.

Приоритет определения маршрута:

1. коды в имени файла;
2. `artifact-card.json`, если он есть;
3. `manifest` или `upload-task`;
4. ручное определение ОПЕРАТОРОМ/КООРДИНАТОРОМ;
5. `blocked`, если маршрут достоверно не определён.

Не следует читать содержимое файла ради маршрутизации, если маршрут однозначно указан безопасными метаданными.

## Завершение маршрута

Копирование файла в локальный `inbox` адресата не завершает межсущностную доставку. Маршрут завершён только после фактической загрузки в адресный чат либо фиксации причины недоставки и следующего шага.

## Внедрение

После утверждения этой редакции:

- новые межсущностные значимые артефакты оформляются по схеме `SRC__name__DST.ext`;
- старые файлы массово не переименовываются;
- переименовываются только артефакты, реально входящие в новый маршрут;
- динамические чатовые ссылки и `filecite` не включаются в тело канона как постоянные ссылки на источники. Вместо них указываются имена документов.

Основание: действующий универсальный файловый канон и project-core требуют коротких имён, проверяемой доставки и минимального документооборота.
